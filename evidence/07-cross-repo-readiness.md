## 1. EP-01 finding 6 materialised — and was resolved without weakening a gate

EP-04 instruction 3 requires encoding the frozen authority notes.
`CROSS_REPO_COMPATIBILITY.md` states them in technology terms: *"runtime
FastAPI traffic reaches PostgreSQL through asyncpg/PgBouncer while
Sqitch/migrations connect directly and bypass PgBouncer"*, and *"no LangGraph
details belong in shared contracts"*.

`compatibility/platform-m0-matrix.yaml` sits on the **scanned release
surface**. A probe confirmed the collision before any design was committed:

```bash
$ # a probe file containing the literal authority notes
$ python3 scripts/check_no_implementation_code.py
check_no_implementation_code: FAIL - 3 prohibited constructs found
  compatibility/__probe.yaml:2: [database-driver] ... (matched 'asyncpg')
  compatibility/__probe.yaml:3: [database-driver] ... (matched 'Sqitch')
  compatibility/__probe.yaml:4: [agent-runtime]  ... (matched 'LangGraph')
```

This is exactly what EP-01 finding 6 predicted: *"prose inside `contracts/`,
`catalog/`, `compatibility/` or `templates/` cannot name prohibited
constructs. That is the deliberate cost of having no ignore-list."*

**Resolution.** Authority is expressed as **roles**, not technologies:

| Frozen note (instruction 3) | Encoded as |
|---|---|
| business authority = `ai-business-api` | `business-authority`, `business-authorization` |
| authentication = `ai-business-auth` | `authentication` |
| DB/stored-function contracts = `ai-business-database` | `database-contracts` |
| agent orchestration only in `ai-business-agent-runtime` | `agent-orchestration` |
| channel adapters = `ai-business-channel-gateway` | `channel-adaptation` |
| admin web: no direct DB/pooling/orchestration access | `direct_datastore_access: forbidden`, `contract_provider: false` |
| central observability = `ai-business-infrastructure` | `deployment-and-observability-infrastructure` |

The technology-level notes stay in `governance/OWNERSHIP.md`, off-surface,
where EP-01 already placed them. **The scanner was not weakened, no ignore-list
was added, and no note was lost.**
`test_authority_is_expressed_as_roles_not_technologies` asserts both halves:
no technology named in the matrix, and every technology still recorded in
`OWNERSHIP.md`.

A second benefit fell out of this. Because roles are an enumerated closed set
rather than free prose, an authority claim is a **value the validator can
compare**. That is what makes §4.4 possible: two repositories claiming
`business-authority` is a detectable collapse, not something a reviewer must
notice while reading.

`dist/contract-manifest.json` is generated by EP-05, so defining its contract
here is a deliberate call rather than scope creep:

  exists — the same contract-first order this repository demands of everyone
  else.

## 3. The lock (`M0-CON-023`)

Three properties make a pin verifiable rather than merely stated, and each is
enforced by the schema rather than left to reviewer diligence:

| Rule | Enforcement |
|---|---|
| version is exact | `pattern` admits only `MAJOR.MINOR.PATCH`; a range fails |
| source is a release | `enum: ["release"]` — a mutable branch cannot be expressed |
| checksums required | `manifest_sha256` and `bundle_sha256` both required, 64 hex chars |

`source` being a single-value enum is the load-bearing detail: consuming
`main` is not a policy someone might violate, it is a document that will not
validate.

The template is **data, not code** (instruction 5).
`test_lock_template_exists_and_is_data_not_code` parses it and asserts its keys
are the lock's keys only, with no installation directive anywhere.
`test_lock_template_placeholders_are_obvious` asserts the **unedited template
fails validation**, so a placeholder cannot ship as a real lock.

`ai-business-admin-web` the `business-authority` role. The validator reports
**two** defects, which is the interesting part:

- `shared-authority` / `wrong-authority` — a second claimant for a role the API owns;
- `unowned-authority` — `admin-presentation` is now claimed by nobody.

An authority moved is both a usurpation and an abandonment, and the matrix
catches both halves.

checksum and asserts both are reported. A consumer fixing a stale lock sees
everything wrong at once rather than one defect per CI round-trip.

## 7. EP-03 finding 3 closed

`validate_catalog.py` now cross-checks each source's `x-contract-version`
against the catalog's `version`. Demonstrated live: setting the error envelope
source to `0.2.0` while the catalog says `0.1.0` produces

```text
validate_catalog: FAIL - 1 catalog defect found
  catalog/contract-catalog.yaml: [version-mismatch] ...: source declares
  x-contract-version '0.2.0', catalog says '0.1.0'.
```

and restoring the file returns exit `0`. Regressed by
`test_source_version_must_match_catalog_version`.

This mattered more than its EP-02 framing suggested. `check_compatibility.py`
reads `x-contract-version` **from the source** to decide whether a breaking
change is covered by a major bump. A divergence could therefore have made a
breaking change appear approved while the catalog still advertised the old
version.
